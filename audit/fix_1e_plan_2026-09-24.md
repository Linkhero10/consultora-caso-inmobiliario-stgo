## 0. Contexto

Durante las dos rondas de revisión ciega de Sol sobre v3.3 (2026-09-24), la mayoría de los
desacuerdos reales se explicaban por `case_mentions` duplicadas o casi-duplicadas dentro del MISMO
documento, generadas por `classify.py` (Etapa 1) — nunca por errores de v3.3 en sí. Se confirmó
hoy, leyendo el código completo: **`classify.py` no tiene ningún paso de deduplicación** de
`case_mentions` dentro de un documento. Una sola llamada LLM (`classify_document`,
`src/classify.py:728-772`) genera la lista completa; nada compara una mención contra otra del
mismo documento después.

**Medición real sobre el corpus completo** (script ad-hoc corrido en esta sesión, no oficial
todavía): de 3885 documentos / 5731 `case_mentions` totales, 1026 documentos tienen ≥2
`case_mentions`. Dos detectores deterministas (nunca fuzzy, mismo criterio que ya usa este
proyecto en Fix 1A): (a) `tipo_objeto_raw` normalizado idéntico dentro del mismo documento → 69
grupos, 174 `case_mentions`; (b) substring bidireccional de la primera `evidencia_objeto_quotes`
(≥8 caracteres) → 71 grupos, 173 `case_mentions`, 70 documentos. Ejemplo extremo: el humedal de
Quilicura tiene **5** `case_mentions` idénticas (mismo objeto, misma comuna, mismo `include`),
solo distinguidas por qué frase del texto citan. Otro patrón real: la misma torre/proyecto con
`decision` **distinta** entre sus copias (`include` en una, `exclude` en otra) — ej. torre
Bellavista.

**Causa probable en el prompt** (`config/classifier_prompt.md:23`): la regla "si necesitas dos
pasajes, crea dos elementos independientes" es para el array de citas DENTRO de una mención, pero
no hay ninguna instrucción explícita sobre cuándo reusar una `case_mention` existente en vez de
crear una nueva — es plausible que el modelo generalice mal esa regla hacia el nivel de
`case_mentions`.

## 1. Decisión y alcance — dos partes, cero costo de LLM

**Prospectivo** (prompt): agregar una regla explícita a `classifier_prompt.md` para que
clasificaciones FUTURAS no repitan el patrón.

**Retroactivo** (determinista, sin re-clasificar nada): un detector nuevo, mismo criterio
`exact_substring`/`exact_match` ya usado en el proyecto, que identifica grupos de `case_mentions`
duplicadas en el corpus YA clasificado y los registra como una tabla NUEVA y ADITIVA —
**ningún `case_mention_id`/`mention_index`/`evidence_id` existente se borra, renumera ni
reescribe** (mismo principio ya aplicado en Fix 1A/1D: "ausencia de fusión ≠ imposibilidad de
fusión, pero nunca se destruye lo que ya existe"). Esto es deliberado: renumerar `case_mentions`
rompería el hash sha256 pinneado en Fix 1D (`build_conflicts.py::CLASSIFICATIONS_SHA256_EXPECTED`)
y cada `case_mention_id` ya referenciado por `evidence`, por las 330 respuestas de v3.3 ya
validadas por Sol, y por `conflict_evidence_backing`.

**Explícitamente FUERA de este fix** (requiere autorización de gasto aparte, no se hace aquí sin
preguntar primero): re-clasificar cualquier documento con LLM. El detector retroactivo opera 100%
sobre `Auditoria/clasificacion/classifications.jsonl` ya existente.

## 2. Cambio de prompt (`config/classifier_prompt.md`)

Agregar, inmediatamente después de la REGLA CENTRAL (línea 9): una regla explícita — si el mismo
caso/objeto real que ya tiene una `case_mention` en este documento vuelve a aparecer descrito en
otro pasaje del texto, esa nueva cita se agrega a `evidencia_objeto_quotes` (o
`evidencia_accion_quotes`/`evidencia_geografica_quotes` según corresponda) de la `case_mention`
YA CREADA para ese objeto — nunca se crea una `case_mention` nueva solo porque el texto lo describe
en una oración distinta. Una `case_mention` nueva solo se justifica cuando el objeto/proyecto real
es genuinamente distinto. Incluir el ejemplo de Quilicura (mismo humedal, mismo `include`, 5
citas) como caso incorrecto explícito de qué NO hacer.

No se re-clasifica el corpus existente con este prompt corregido en este fix.

## 3. Detector retroactivo determinista

Nuevo script `src/detect_case_mention_duplicates.py`. Reutiliza `_norm()`:

- Por documento, dos criterios (unión, nunca intersección), nunca fuzzy:
  1. `tipo_objeto_raw` normalizado IDÉNTICO.
  2. Substring bidireccional de la primera `evidencia_objeto_quotes` no vacía.
- Union-find dentro de cada documento para agrupar transitivamente.
- `canonical_case_mention_id` por grupo: preferir `decision='include'`; si hay `decision` mixta,
  registrar explícitamente `decision_mixed_in_group=1`.
- Grupos de tamaño 1 también quedan en la tabla, como su propio canonical.

## 4. Tabla nueva `case_mention_duplicate_link`

```sql
CREATE TABLE case_mention_duplicate_link (
    case_mention_id TEXT NOT NULL PRIMARY KEY REFERENCES case_mention(case_mention_id),
    document_id TEXT NOT NULL,
    duplicate_group_id TEXT NOT NULL,
    canonical_case_mention_id TEXT NOT NULL REFERENCES case_mention(case_mention_id),
    group_size INTEGER NOT NULL CHECK (group_size >= 1),
    match_method TEXT NOT NULL CHECK (match_method IN ('single', 'tipo_objeto_raw_exact', 'quote_substring', 'ambos')),
    decision_mixed_in_group INTEGER NOT NULL CHECK (decision_mixed_in_group IN (0, 1))
);
```

## 5. Consumir la tabla nueva en Fix 1D

En `_project_backing_evidence()`, rama v3.3: cuando el `case_mention_id` que v3.3 indicó no tiene
por sí solo evidencia `objeto` verificada, pero su `canonical_case_mention_id` (o cualquier miembro
de su grupo) SÍ la tiene, usar esa evidencia igual — con
`match_method='v3_3_verified_index_via_duplicate_group'` explícito, nunca silencioso.
